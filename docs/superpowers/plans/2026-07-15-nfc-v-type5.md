# NFC-V / Type 5 (ISO 15693) Read Support Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add read support for NFC-V / ISO 15693 (NFC Forum Type 5) tags — the last major tag family the library can't read at all — via a `Type5Tag` driver behind the same transport-interface architecture the other five families use, so it reads identically on the phone antenna (and on the rare CCID reader that supports 15693).

**Architecture:** Extends the transport layer from Plans 2-3. A new `NfcVTransport` interface, a `Type5Tag` driver over it, an Android backend implementing it via `android.nfc.tech.NfcV`, a `TagTechHint.type5` for detection, and the Kotlin reader-mode side polling `FLAG_READER_NFC_V`. The CCID backend provides `nfcV()` for interface completeness but it is a "not supported by this reader" stub — see the hardware reality below.

**Tech Stack:** Flutter 3.38.3 / Dart SDK `>=3.5.0 <4.0.0`, Kotlin (`android.nfc.tech.NfcV`, min SDK 26), `flutter_test`. No new dependencies.

## Global Constraints

- **NFC-V is phone-only in practice.** The ACR122U (this project's validated reader) is PN532-based and does NOT support ISO 15693 — it cannot even activate a Type 5 tag in its RF field. So a Type 5 tag on that reader is never detected (the reader shows no card). NFC-V read is therefore a **built-in-NFC feature**; the CCID `nfcV()` exists only to satisfy the `TransportBackend` interface and returns a transport whose reads throw a clear "reader does not support ISO 15693" error. Do NOT try to make the ACR122U read 15693. (Other CCID readers, e.g. ACR1252U, do support it; their pseudo-APDU dialect is out of scope here — leave a `TODO` noting a future reader-specific backend could implement it.)
- **The transport interfaces stay additive.** Add `NfcVTransport` and `TransportBackend.nfcV()`; do NOT change the five existing interfaces or the existing backends' behavior. All existing drivers keep working unchanged.
- **The read model is ISO 15693 block reads.** Type 5 memory is block-addressed (typically 4-byte blocks). Identity comes from the discovery (UID, DSFID) with no I/O; data reads use `NfcV.transceive` with raw ISO 15693 command frames.
- **Zero behavior change to existing families.** `identifyTag`, the CCID path, and the other five drivers are untouched except for the additive `nfcV()`/hint/`Type5Tag` wiring.
- **Test baseline: 209 library tests + 19 example tests, 0 failing.** Every Dart task adds tests; counts may only go up. The Kotlin task adds none (not unit-testable) but must not drop the count.
- `flutter analyze` clean (2 pre-existing info-lints in `example/test/mrt_transaction_test.dart` expected). `flutter pub publish --dry-run` 0 warnings, archive < 1 MB. Do NOT touch `LICENSE`.

## The one thing only hardware can settle

The entire Type 5 read path is validated only on a physical NFC phone with a real ISO 15693 tag (ICODE SLIX is the common, cheap one; HID iCLASS is 15693 but access-controlled). The Kotlin `NfcV` calls and the exact ISO 15693 command framing (flags byte, addressed vs non-addressed mode) cannot be unit-tested. This is the plan's acceptance gate.

- Produces:
  - `abstract class NfcVTransport` (in `transport.dart`):
    ```dart
    /// Transport for an NFC-V / ISO 15693 (NFC Forum Type 5) tag.
    ///
    /// Method-based reads over block-addressed memory. Identity (UID, DSFID)
    /// comes from tag discovery with no I/O. `readBlock`/`readMultipleBlocks`
    /// issue ISO 15693 commands; on the CCID backend these throw because the
    /// ACR122U does not support ISO 15693 (this transport is built-in-NFC in
    /// practice).
    abstract class NfcVTransport {
      Uint8List get uid;
      /// Data Storage Format Identifier, or null if the source didn't report it.
      int? get dsfid;
      /// Reads one memory block (typically 4 bytes) at [blockNumber].
      Future<Uint8List> readBlock(int blockNumber);
      /// Reads [count] blocks starting at [firstBlock], concatenated.
      Future<Uint8List> readMultipleBlocks(int firstBlock, int count);
      /// ISO 15693 "Get System Information" (0x2B) raw response, or null if
      /// unsupported. Carries block count/size, DSFID, AFI, IC reference.
      Future<Uint8List?> getSystemInfo();
    }
    ```

  - `enum TagTechHint { type2, mifareClassic, felica, isoDep, typeB, type5 }` (append `type5`).

(It is never reached via CCID detection — the ACR122U can't activate a Type 5 tag — but the interface must be satisfied.) Add one test asserting `readBlock` throws that message.

### Task 2: `Type5Tag` driver + `Type5TagInfo` + reads

Pure driver logic over `NfcVTransport`, tested against a fake transport. This is where the ISO 15693 read semantics and the Type 5 NDEF walk live.

**Files:**
- Create: `lib/src/tag/type5.dart`, `test/tag/type5_test.dart`
- Modify: `lib/nfc_hub.dart` (export `Type5Tag`, `Type5TagInfo`)

**Interfaces:**
- Consumes: `NfcVTransport` (Task 1), the NDEF parser (`parseTlvForNdefMessage`/`parseNdefRecords` from `lib/src/ndef.dart` — reused as-is).
- Produces: `Type5Tag(NfcVTransport transport, {Uint8List? atr})` extending `TagDriver`, with:
  - `Future<Type5TagInfo> readTagInfo()` — `Type5TagInfo implements TagInfo` with `technology = 'NFC-V / ISO 15693 (Type 5)'`, `uid` = `transport.uid`, `atr`, plus `dsfid`.
  - `Future<Uint8List> readBlock(int block)` → `transport.readBlock(block)`.
  - `Future<Uint8List> readMemoryDump({int maxBlocks = 256})` — reads blocks from 0 upward via `readBlock`, stopping on the first read failure or `maxBlocks`, concatenating (mirror `Type2Tag._readPagesFrom`'s break-on-failure loop).
  - `Future<List<NdefRecord>> readNdef()` — reads the Type 5 CC (block 0) + data blocks, TLV-parses, returns records. The Type 5 CC: byte 0 is the magic (`0xE1` or `0xE2`); it's NDEF-formatted if magic is `0xE1`/`0xE2`; MLEN is byte 2 (× 8 = data-area bytes for the 4-byte CC form). Walk blocks from 1 (the CC occupies block 0 in the common 4-byte-block layout) concatenating until MLEN bytes read, then `parseTlvForNdefMessage` → `parseNdefRecords`. Throw a clear exception if the CC magic isn't `0xE1`/`0xE2` ("Tag is not NDEF-formatted"). Reuse the exact TLV/record functions from `ndef.dart`.

- [ ] **Step 1: write failing tests** in `type5_test.dart` against a `_FakeNfcVTransport` (records `readBlock` calls, returns scripted 4-byte blocks; fixed `uid`/`dsfid`):
  - `readTagInfo()` returns technology/uid/dsfid.
  - `readBlock(3)` calls `transport.readBlock(3)` and returns its bytes.
  - `readMemoryDump()` reads from block 0 upward and stops when a `readBlock` throws (assert it returns what it read, doesn't propagate).
  - `readNdef()` with a scripted CC block (`E1 40 <mlen> 00`) + a TLV+Text-record spread across blocks decodes to the expected Text record. (Hand-construct the block bytes; reuse the NDEF fixture shape from `test/ndef_test.dart`.)
  - `readNdef()` throws "not NDEF-formatted" when the CC magic isn't `0xE1`/`0xE2`.

### Task 3: Android `NfcVTransport` + detection wiring

The real `_AndroidNfcVTransport` over `AndroidNfcManager`, plus the `hintFromTechList` and `identifyFromBackend` cases that route a Type 5 discovery to `Type5Tag`. Tested against a fake manager.

**Files:**
- Modify: `lib/src/transport/android_backend.dart`, `lib/src/source/android_source.dart`, `lib/src/tag/detection.dart`, `lib/src/platform/android_nfc_manager.dart`
- Modify test: `test/transport/android_backend_test.dart`, `test/source/android_source_test.dart`, `test/transport/backend_identify_test.dart`, `test/platform/android_nfc_manager_test.dart`

**Interfaces:**
- Consumes: `NfcVTransport`, `AndroidNfcManager`, the discovery type.
- Produces: `_AndroidNfcVTransport` mapping:
  - `uid` / `dsfid` → from `discovery` (Kotlin populates them in Task 4; `dsfid` is a new nullable `int?` on `NfcTagDiscovery`).
  - `readBlock(b)` → `manager.transceive(h, 'NfcV', <ISO15693 Read Single Block frame>)`, returning the block data (strip the 1-byte response flags at index 0). **The frame: `[0x02, 0x20, b]`** (flags `0x02` = high data rate, non-addressed — valid with a single tag in field; `0x20` = Read Single Block; `b` = block number). Response: `[flags, ...blockData]` — return `response.sublist(1)`. (Note: the exact flags byte is a hardware-validation detail; `0x02` is the common working value. Document this in a `///`.)
  - `readMultipleBlocks(first, count)` → `[0x02, 0x23, first, count-1]` (`0x23` = Read Multiple Blocks; the count field is N-1 per ISO 15693). Strip the response flags byte.
  - `getSystemInfo()` → `[0x02, 0x2B]`; return the response or null on error (catch → null, never throw).
  - `TagLostException` mapping on every `transceive` (the `PlatformException(code:'TAG_LOST')` → `TagLostException`), same as the other Android transports.
- `AndroidTransportBackend.nfcV()` → `Future.value(discovery has NfcV identity ? _AndroidNfcVTransport(...) : null)`.
- `hintFromTechList`: add `if (has('android.nfc.tech.NfcV')) return TagTechHint.type5;` — place it appropriately (NfcV is its own RF tech, no precedence conflict with A/B/F; add it near the others, e.g. after MifareClassic or at the end before the NfcA fallback — it will never co-occur with NfcA/B/F, so order among those doesn't matter, but keep it BEFORE any generic fallback).
- `identifyFromBackend` hint switch: add
  ```dart
  case TagTechHint.type5:
    final nfcV = await backend.nfcV();
    if (nfcV == null) {
      throw const UnrecognizedTagException(
          'Type 5 hinted but no NFC-V target present');
    }
    return Type5Tag(nfcV, atr: atr);
  ```
- `NfcTagDiscovery`: add `final int? dsfid;` (decoded from the discovery event map key `'dsfid'`; nullable).
